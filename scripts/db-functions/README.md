# DB関数（RPC）変更の管理

HT・ゲートが Supabase の `rpc()` で呼ぶ関数と、その他の `public` スキーマの関数を手で変更したときのSQLとロールバックSQLを置く場所です。**フォルダの意味・共通の運用ルール・適用手順は [`../README.md`](../README.md) にまとめてあります。**

ファイル名は `YYYYMMDD-対象.sql` / `.rollback.sql`。各ファイルの1行目に `-- 適用状況: ステージング YYYY-MM-DD / 本番 YYYY-MM-DD` を書きます。

**★ 関数の変更はテーブル変更と順序が結びつくことが多いので、[`../README.md` の「フォルダをまたぐ適用順序」](../README.md) を必ず確認してください。**

## 20260924: 移動の送信RPC3本の修理

`t_ido_result` / `t_ido_ctn_result` に列を足すと composite 型が 11列 → 13列になります。送信RPC（`ido_send_20260716_1` / `rf_ido_send_20251225_1` / `el_ido_send_20251225_1`）の中の `row(...)::t_ido_result` は列の個数と物理順に依存しているため、**列追加だけを適用するとHT・ゲートからの実績送信が全部落ちます**。

```
ERROR:  cannot cast type record to t_ido_result
DETAIL: Input has too few columns.
```

→ `db-tables/applied/20260924-ido-juchu-meisai.sql` と**必ず連続で、できれば同一トランザクションで**流してください。ビュー側の3本（`db-views/applied/` の `v_ido_den3_lst` / `v_ido_den3_result` / `v_ido_den2_meisai_lst`）はこの2本の後です。

⚠️ この修理は「要素数合わせ」だけで、受注2列には常に0が入ります。そのため**複数明細にまたがる機材では、同じ機材の明細行すべてに機材合計の読取数が入ります**（1機材2明細でタグ1本を読むと両方が read = 1）。これを解消するのが次の `20260925-ido-send-rpc` と、HT・ゲート側の改修です。

## 20260925: 移動の送信RPCの統合

既存3本は関数名と schema 修飾の有無を除いて中身が完全に同一でした（本番・ステージングとも正規化 diff で差分0）。`el_` だけコンテナ側の `upd_user` がずれるという写経由来のバグも生じていたため、`ido_send_20260925` 1本に統合しました。

**既存3本はそのまま残しています。** HT・ゲートが乗り換えるまで動き続ける必要があるためです。両アプリの移行が完了したら `20260925-ido-send-rpc.rollback.sql` の末尾にある後片付け用 DROP を流してください。

処理はすべて本体に入っており、既存3本と同じ構成です（作業指示日の最新化 → UPSERT → 伝票の読取数の更新）。違いは2点だけです。

1. UPSERT が受注2列を書く
2. 読取数の集計が **6キー → 8キー**（受注2列を足す）。6キーのままだと同じ機材の明細行すべてに機材合計が入ってしまう。あわせて「実績があったグループ」だけでなく実績が動いた機材の全明細を数え直す（タグが1本も割り当たらなかった明細を0に戻すため）

### ★ どのタグがどの明細のものかは「アプリが決める」

HT・ゲートは読取時にすでに「同じ機材の行を上から埋め、予定数に達したら次の行へ」という充当を画面上で行っています（HT: `kizai_list_grid_row_provider.dart` の `preModelList` ループ、ゲート: `MovementListForm.cs` の `FirstOrDefault(... ResultQty < PlanQty ...)`）。リストを明細単位（`v_ido_den2_meisai_lst`）にすれば、このループがそのまま明細への充当になります。アプリは充当先の行が持つ `juchu_head_id` / `juchu_kizai_head_id` を実績に載せて送ります。

**RPCはその2列をそのまま保存するだけで、紐づけの判断はしません。** DB側でも判断すると、画面に見えているものと保存されるものが食い違う余地が生まれるためです。

### ⚠️ この関数は「受注2列を送るアプリ専用」

受注2列を送らない旧版のHT・ゲートがこれを呼ぶと、タグはすべて `0/0` で保存され、**受注明細の伝票行は読取数0のままになります**（明細単位で数えるため）。旧版は既存3本を呼び続けます。乗り換えは「ビュー差し替え＋受注2列の送信」と同時に行います。

なお、既に紐づいているタグを `0/0` で再送しても割り当ては消えません（`excluded.juchu_head_id <> 0` のときだけ上書きする）。移行期に新旧のアプリが混在しても、既存の紐づけは壊れません。

## 20260930: ゲート入出庫送信RPCの dsp_ord_num 対応（staging-only）

返却・キープの入庫で「親機材として読んだタグ」（明細ID null ＋ 対応表付き）の扱いを直します。関数名・引数は変えません。

- 採番キーに親の `dsp_ord_num` を足し、同じ機材・同じ `dsp_ord_num` の伝票行があればその明細IDを再利用する
- 伝票の `dsp_ord_num` は GROUP BY に入れず `max()` で取り、`on conflict` では NULL の行だけ埋める
- 対応表との照合から作業日時を外す

**修正前のゲートとも互換**です（同じ機材なら1回の送信で親の `dsp_ord_num` が1つしかないため結果は同じ。画面を開いたまま2回目を送ると明細が分かれずまとまる点だけが変わる）。本番は **この関数 → ゲートのアプリ** の順に更新すること。逆順だと、同じ機材を親の2行にまたがって送ったときに `ON CONFLICT DO UPDATE command cannot affect row a second time` で送信が落ちます（2026-09-30 にステージングで再現・解消を確認）。

ロールバックファイルは**本番の適用前の定義そのもの**です。本番に流す直前に `md5(pg_get_functiondef(...))` がファイル冒頭の値と一致するか確認してください（ステージングの適用前の定義は `public.` 修飾の有無だけが違い、処理は同一）。

## 20260930: HT入出庫送信RPCの dsp_ord_num 対応

HT の `nyushuko_send_20260626_1` は、ゲートの修正前と「入庫チェックの伝票 UPSERT を区分で分岐していた」点だけが違いました（返却・キープでは `dsp_ord_num` を入れていなかった）。分岐をなくしてゲートの修正後と同じ本体にし、HT 用に次を足しています。関数名・引数（`juchu_kizai_head_kbn` を含む）は変えておらず、**HT アプリの修正は不要**です。

- HT は親機材として読んだタグに**親の明細ID**を付けて送ってくる。区分が通常以外で対応表にあるタグは、その明細IDを使わずゲートと同じ採番（同じ機材・同じ `dsp_ord_num` の行を再利用 → 無ければ max + 1）で振り直す
- 再利用の探索では、修正前に HT が作った行（`dsp_ord_num` NULL・明細ID＝親の明細ID）も対象にする（途中まで送った返却が分かれないように）
- `on conflict` で `dsp_ord_num` の NULL を埋めるのは**未到着の受注機材ヘッダー・作業場所だけ**。到着時に親から引かれていない行を後から紐づけると、到着解除で引いていない数量が親に戻り、親の入庫予定が増えるため

修正前に作られた行（`dsp_ord_num` NULL）を親の値で埋めるデータ補正 `20260930-nyushuko-den-dsp-backfill` も用意していましたが、流さないことにして 2026-10-19 に削除しました（`db-data/README.md` 参照）。

## 20261002: ゲート入出庫送信RPCの予定数引き上げ（HT に合わせる。staging-only）

## 関数を書くときの注意

- **`CREATE OR REPLACE FUNCTION` は冪等**ですが、引数の型や名前を変えると**別の関数として増えます**。同名・別シグネチャが並ぶと PostgREST がどちらを呼ぶか曖昧になるので、シグネチャを変えるときは旧い方の `DROP` も書いてください
- **`GRANT EXECUTE` を確認すること**。`public` スキーマの default privileges はステージングに無いので、新規関数は明示的に付与が要る場合があります
- 関数の中で `row(...)::<テーブル名>` を使っている箇所は、**そのテーブルの列を足すだけで壊れます**。テーブル変更の影響調査では `pg_get_functiondef` の全文検索を必ず行ってください
- 本番とステージングで定義を比べるときは `pg_get_functiondef` の全文を diff します。schema 修飾の有無だけが違うことがあるので、`public.` を落としてから比較してください
